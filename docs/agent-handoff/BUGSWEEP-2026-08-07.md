## P0 — correctness

### 1. Cross-browser handles are never validated; `group_tabs` can act on the WRONG tab **[live]**

`daemon/index.ts` accepts a second handle for a command without checking it
belongs to the same browser as the first. Proven live from the TUI: moving a
**Chrome** tab into a **Safari** window was accepted and produced

```
move failed: Tool "move_tab" failed: No window with id: 38.
```

`38` is the Safari window's *internal numeric id*, passed straight into
`chrome.tabs.move`. `extNum()` (`daemon/index.ts:122`) only checks the handle is
extension-generation — never `parsed.browser`.

Affected sites: `move_tab` targetWindowId (`:177`) and targetGroupId (`:181`),
`open_tab` windowId/groupId (`:215`,`:218`), `group_tabs`
tabIds/groupId/targetWindowId (`:275`,`:276`,`:278`).

**Worst case — silent wrong action, not an error.** `group_tabs` infers the
browser from **only `tabIds[0]`** (`:261`), then numeric-converts the rest with no
check. A mixed list `[t:chrome:x111, t:safari:x222]` routes to Chrome and sends
`[111, 222]`; if Chrome happens to own a tab `222`, **the wrong tab is grouped**
and the call reports success.

*Fix direction:* one `requireSameBrowser(anchor, ...handles)` helper used at every
multi-handle site; actionable error naming both browsers. Also violates guardrail
#4 (bare `error.message` leaked instead of `wrapToolError`).

### 2. `set_window` silently drops `state` when `bounds` is also given **[live]**

```
$ browser-tab window set w:chrome:x… --bounds 200,200,800,600 --state normal
{ "ok": true, … }
# result: x=200 y=200 applied,  state STILL "minimized"
```

`packages/extension-core/src/commands.ts:196` `setWindowOutcome` uses
`if (args.bounds) {…} else if (args.state) {…}` (`:205`) — bounds wins, `state`
is discarded with **no error and `ok:true`**. The natural "restore this window
and place it" call half-executes and reports success. Same `else if` shape at
`:182` in `openWindowOutcome`.

*Fix direction:* apply bounds and state in sequence (Chrome forbids them in one
`update`, so two calls), or reject the combination explicitly. Never silently drop.

### 3. TUI corrupts its own render on terminals shorter than ~28 rows **[live]**

At 200×**20** the fixed 24-row list overflows the flex container and **overwrites
the chrome**:

```
 ▸ safari — 1 windows, 24 tabs [extension] AI, Instant Vide  https://elevenlabs.io/…   ← two rows overprinted
 …several rows silently missing…
 j/k move ·  r⏎ focus ·  (x close ·  …                       engine: rust             ← status bar destroyed,
                                                                                        bled into help bar
```

Rows vanish, two rows print on one line, and the **status bar is gone entirely**.
Fully recovers when the terminal grows back, so it is pure overflow, not state
corruption. Root cause is the same constant as finding #4.

## P1

### 4. TUI list never fills the terminal — the reported viewport bug **[live]**

`apps/browser-tab-mcp/src/tui/App.tsx:22` — `const VIEWPORT = 24;` is a
compile-time constant. It is never derived from `stdout.rows` and there is no
resize listener.

Measured at 200×50 with 34 rows in the model: **24 rows rendered, 22 blank rows
wasted** (lines 26–47).

Second, related defect at `:142`:

```ts
const visibleStart = Math.max(0, clampedCursor - Math.floor(VIEWPORT / 2));
const visible = rows.slice(visibleStart, visibleStart + VIEWPORT);
```

`visibleStart` is never clamped to `rows.length - VIEWPORT`, so the window
*shrinks* as you approach the end. Measured with `G`: **13 rows rendered, 33
blank**.

*Fix direction:* derive the viewport from Ink's `useStdout().stdout.rows` minus
chrome height (header + separator + status + help), subscribe to `resize`, and
clamp `visibleStart` to `[0, max(0, rows.length - viewport)]`. `tui-kit` already
has `ink-testing-library@^4` as a devDependency and **zero render tests** — that
is why this shipped.

### 5. REPL: `raw` is 100% broken and 15 of 18 advertised tools are uncallable **[live]**

```
browser-tab> daemon_status
Unknown command: daemon_status. Type 'help' for available commands.

browser-tab> raw {"name":"daemon_status","arguments":{}}
Expected property name or '}' in JSON at position 1 (line 1 column 2)

browser-tab> raw {\"name\":\"daemon_status\",…}      # escaping does not help
Expected property name or '}' in JSON at position 1 (line 1 column 2)
```

Two independent defects:

- `parseConsoleInput` (`packages/cli-kit/src/repl.ts:60`) treats `"` and `'` as
  shell quoting and **consumes every quote character**, so `{"name":…}` becomes
  `{name:…}` — invalid JSON. There is no escape hatch; `raw` cannot work at all.
- The docblock (`repl.ts:8`) promises `<tool> <json>` dispatch, but only `help`,
  `tools`, `raw`, `quit`/`exit` and registered shortcuts are handled (`:173`).
  `help` nonetheless prints all 18 MCP tools under **"Available MCP tools:"** —
  actively misleading.

Net: the whole console mode is `health`, `list`, `noop`. `packages/cli-kit` has
**no `repl.test.ts`** — which is why both shipped.

**Decision taken:** fix `raw` *and* implement the promised generic `<tool> <json>`
dispatch so all 18 tools are callable.

### 6. TUI / daemon client never reconnects — silent freeze on daemon restart **[read]**

`DaemonClient.subscribe` (`client/daemon-client.ts:117`) registers a handler and
sends `subscribe`; there is **no `close`/`error` handler and no reconnect**.
`tui/useSnapshot.ts` only falls back to polling if the *initial* subscribe throws
— once `live=true` it never re-checks.

So if the daemon restarts (`browser-tab daemon restart`, a launchd respawn, a
crash) while the TUI is open, the TUI **freezes on stale data while still
displaying "daemon stream"**. PR-D verified the *extension* reconnects in <2s;
nobody checked the *client*.

*Fix direction:* on socket close → flip `live=false`, start polling, and retry
subscribe with backoff.

### 7. `focus_tab` scope + return object — **re-scoped by user decision**

Live result: the **extension** path *does* un-minimise
(`windows.update(id,{focused:true})` at `extension-core/src/commands.ts:221`
restored `state: minimized → normal`), while the **AppleScript** path
(`detect/adapters/chromium.ts:158`) does `set active tab index` / `set index of w
to 1` / `activate` and **never clears `minimized`**. Two paths, two behaviours.

**User's ruling (verbatim intent):** `focus_tab`'s job is *only* to make the
selected tab active in its window. Whether the window is visible, focused,
minimised, on another space or monitor is **the window manager's concern**.
browser-tab should "simply make sure it returns enough info / data / object so
that the tool knows the state of it, can find it and work with it if needed."
The user is explicitly *not convinced the window should be raised/un-minimised at
all*.

Evidence supporting this split: for the scratch window, browser-tab reported
`cgWindowId: 140001` and `yabai -m query --windows --window 140001` returned
`display:1, space:4, is-visible, is-minimized` — i.e. **yabai already indexes the
exact id browser-tab emits**, so the WM needs nothing more than the id.

*Fix direction (needs a call on the default — see Open questions):*
1. Make the two paths consistent and **minimal** — activate the tab, stop there.
2. Make window raising an explicit opt-in (`raiseWindow?: boolean`) rather than
   an implicit side effect.
3. Enrich the result so the caller can act without a second `list_tabs`:
   `cgWindowId`, `windowState`, `wasMinimized`, `windowFocused`.

⚠️ Changing the default is a **contract change** — today's `focus_tab` raises the
window, and the TUI's `Enter` relies on it.

## P2 — quality / consistency

### 8. CLI has no human-readable output; 19 of 22 `cli-kit` exports are dead **[live]**

`browser-tab list` with **no** `--json` prints raw JSON, identical to `--json`.
`mcp-kit/src/dispatch.ts:114` makes every text block
`JSON.stringify(result, null, 2)`, and `cli.ts` `printResult` (`:37`) just echoes
it.

Meanwhile `cli-kit/src/output.ts` documents exactly the right behaviour
("human form when stdout is a TTY, JSON otherwise") and implements
`printTable` / `printAuto` / `printJson` / `resolveOutputMode` — **all unused**.
Dead exports: `printAuto`, `printTable`, `printJson`, `resolveOutputMode`,
`OutputMode`, `OutputFlags`, `TableSpec`, `isCI`, `isStdoutTTY`, `isStdinTTY`,
`isStderrTTY`, `colorEnabled`, `disableColors`, `buildProgram`, `ProgramOptions`,
`bindEnvFlags`, `applyEnvFromFlags`, `EnvFlagBinding`, `BinderOptions`.

Confirmed working, no bug: global-flag placement (`list --json` and `--json list`
both fine) and exit codes (1 on error, 0 on success).

**Decision taken:** wire human tables for the read commands, keep `--json`
(and auto-JSON when piped / CI) for machines.

### 9. AGENTS.md states an env↔flag rule that is not implemented **[live]**

`AGENTS.md:149`: *"**Rule**: every recognized env var is also accepted as a CLI
flag (binder in `@george43g/cli-kit/env-flag-binder`). `MCP_LOG_DIR` ↔
`--log-dir`, `MCP_DISABLE_NATIVE` ↔ `--disable-native`, etc."*

`browser-tab --help` offers only `--json`, `-q`, `-v`, `--no-color`. The binder is
**never called anywhere**. Either wire it or delete the rule + the binder.

### 10. `history` silently omits disabled sources **[live]**

`--browser safari` gives an excellent, actionable error:

```
Safari history is disabled. Set BROWSER_TAB_SAFARI_HISTORY=1 (needs Full Disk
Access — see `browser-tab doctor`) to enable reading Safari's History.db.
```

But **omitting** `browser` merges only reachable sources and silently returns
Chrome-only rows. Searching for something you saw in Safari returns nothing with
no hint why. (Verified the query filter itself is *fine*: `suno`→2, `Suno`→2
case-insensitive, `example`→1; `github`→0 is genuine — those URLs were Safari
tabs.)

*Fix direction:* add a `sources` field to the result, e.g.
`{ chrome: "ok", safari: "disabled: set BROWSER_TAB_SAFARI_HISTORY=1" }`.

### 14. TUI move mode offers impossible and no-op targets **[live]**

`tui/App.tsx:43` — `moveTargets = rows.filter(r => r.kind === "window")` includes
**every** window across **every** browser. Observed live:

- Default target (`targetIdx = 0`) is the tab's **own** window → a no-op self-move.
- Safari windows are offered for a Chrome tab → the finding #1 failure.

*Fix direction:* filter to same-browser windows and default to the first window
that is not the tab's own.

## Deferred: release automation (research, no decision yet)

User wants "done properly — git tags, releases, changelogs" but **not locked to
npm publishing**, and is open to modern alternatives to semantic-release.

Current state: `.releaserc.json` exists and already produces tags + GitHub
releases + `CHANGELOG.md`; **only the `@semantic-release/npm` plugin ties it to
npm**. `release.yml` is `workflow_dispatch`-only. semantic-release is **not even
in `package.json`** — the config is orphaned.

Options to weigh in the plan:

1. **Keep semantic-release, drop the npm plugin** (or `npmPublish:false`).
   Zero new tooling; gets tags + releases + changelog immediately. Least work,
   least "modern".
2. **release-please** (Google). Conventional-commits → a rolling *Release PR*;
   merging it bumps versions, writes the changelog, tags, and creates the GitHub
   Release. **Publishing is a wholly separate job you simply don't add** — the
   cleanest fit for "everything but npm". Manifest mode + `node-workspace` plugin
   handles this monorepo with per-package tags.
3. **changesets** (Atlassian). Best-in-class monorepo support; explicit changeset
   files instead of inferring from commits; `changeset version` does
   versions+changelogs without any publish step. More ceremony per PR.
4. **release-it** — flexible, hooks-based, `npm.publish:false`; more manual.

Also folded in here (previously separate): the **bin version `0.0.0`** (shown by
`--version` and in the TUI header) and whether the **extension manifest** version
(currently `0.2.0`, bumped manually via PR #21's `run bump`) should be driven by
the same mechanism.

## Test plan — no regressions

**The e2e harness already does the robust thing** (finding #11), so the answer to
"mock the browser or launch a real one" is: *it already launches a real one —
extend it, do not rebuild it.* `apps/chrome-extension/e2e/fixtures.ts` loads the
**built `dist/`** into a real Chromium (new-headless — the full chromium build
supports MV3 extensions, the headless shell does not) and wires it to a throwaway
daemon isolated by `BROWSER_TAB_STATE_DIR`/`_CACHE_DIR`. That matches current best
practice for MV3 extension e2e. Existing coverage is only 3 tests: options page
renders · daemon serves x-handles · cross-window move preserves scroll.

New tests, by layer:

| Finding | Layer | Test |
|---|---|---|
| 1 cross-browser handles | unit + e2e | `requireSameBrowser` rejects mismatches at every site; e2e asserts an actionable error, not a leaked numeric id |
| 1 group_tabs anchor | unit | mixed-browser `tabIds` must **error**, never group |
| 2 bounds+state | unit + **e2e** | `set_window {bounds, state}` applies both; e2e asserts real window state |
| 3 + 4 viewport | **unit (new)** | `ink-testing-library` (already a devDep, unused): render at heights 20/24/50, assert row count == available height, no overflow, `visibleStart` clamped at `G` |
| 5 REPL | **unit (new)** | first-ever `repl.test.ts`: `raw` round-trips JSON with quotes; `<tool> <json>` dispatches; `help` lists only callable commands |
| 6 reconnect | integration | kill the daemon under a live subscription → client flips to polling and re-subscribes |
| 7 focus_tab | e2e | activates the tab; result carries `cgWindowId`/`windowState`; window raising only when opted in |
| 8 CLI output | unit | TTY → table, piped/`--json`/CI → JSON (`resolveOutputMode` finally exercised) |
| 10 history sources | unit | `sources` field reports disabled Safari |
| 14 move targets | unit | `moveTargets` excludes other browsers and the tab's own window |

Plus: **sabotage-check every new guard test** (invert the logic → red), per the
standing bar, and keep `pnpm stress` green.
